## 4. Часть 1. Аналитические запросы

### 1.1. Сравнение объектов внутри групп

**Задача:** составить рейтинг популярности фильмов внутри каждого жанра по числу просмотров. Фильмы с одинаковым числом просмотров должны занимать одинаковое место. Фильмы без просмотров не должны пропасть из результата.

**Как работает:**
- `LEFT JOIN viewing_history` сохраняет все фильмы, даже без просмотров, а `COUNT(vh.history_id)` для них даёт `0` (а не `NULL`).
- `RANK() OVER (PARTITION BY g.genre_id ORDER BY COUNT(...) DESC)` нумерует фильмы **отдельно в каждом жанре** (`PARTITION BY`) по убыванию просмотров. Равные значения получают равное место.
- Рядом выведен `DENSE_RANK()`, чтобы была видна разница: после совпадения `RANK` пропускает номера (1, 1, 3), а `DENSE_RANK` нет (1, 1, 2).
- Рейтинг фильма `NULL` (нет данных) не мешает: фильм остаётся в результате.

**Контрольный результат** (жанр `Western`), так он и выводится в `03_control_check.sql`:

| Фильм | Просмотров | RANK | DENSE_RANK | Комментарий |
|---|---|---|---|---|
| Control Western A | 3 | 1 | 1 | совпадение |
| Control Western B | 3 | 1 | 1 | совпадение |
| Control Western C | 1 | 3 | 2 | место 2 пропущено в `RANK` |
| Control Western D | 0 | 4 | 3 | нет просмотров, нет рейтинга, но фильм в результате |

На основных данных тоже видны совпадения: во всех трёх триллерах по 3 просмотра (все на первом месте), в драме три фильма без просмотров делят второе место.

### 1.2. Анализ последовательности событий

**Задача:** для каждого пользователя определить, сколько дней прошло между его последовательными просмотрами. Первый просмотр пользователя тоже должен быть в результате.

**Как работает:**
- `LAG(vh.watched_at) OVER w` берёт значение из **предыдущей строки** того же пользователя. Для первой строки предыдущей нет, поэтому получается `NULL`. Строка при этом не теряется (в отличие от самосоединения через `JOIN`).
- `WINDOW w AS (PARTITION BY vh.user_id ORDER BY vh.watched_at, vh.history_id)`: порядок задан **однозначно**. Если у двух просмотров одинаковое время, их порядок определяет `history_id`. Без этого второго ключа сортировки порядок равных строк был бы случайным.
- `vh.watched_at::date - LAG(vh.watched_at::date) OVER w` вычитает даты и даёт число дней. Рядом выводится и название предыдущего фильма.

**Контрольный результат** (`Control Viewer One`):

| Фильм | Время | Предыдущее | Дней |
|---|---|---|---|
| A | 2026-03-01 10:00 | пусто | пусто |
| B | 2026-03-05 20:00 | 2026-03-01 | 4 |
| C | 2026-03-05 20:00 | 2026-03-05 (фильм B) | 0 |
| A | 2026-03-15 18:00 | 2026-03-05 (фильм C) | 10 |

У `Control Viewer Two` интервалы 1 и 8 дней. «Предыдущее» считается заново, ничего не берётся от первого пользователя.

### 1.3. Вклад отдельных операций в общий показатель

**Задача:** для каждой оплаченной подписки показать её стоимость, общую сумму трат пользователя и долю подписки в этой сумме. Каждая подписка остаётся отдельной строкой.

**Как работает:**
- `SUM(p.price) OVER (PARTITION BY a.user_id)` считает сумму по пользователю, **не схлопывая строки** (как это делал бы `GROUP BY`). Поэтому есть и стоимость отдельной подписки, и общая сумма.
- `ROUND(100.0 * p.price / SUM(...) OVER (...), 1)` даёт долю в процентах.
- `WHERE a.status <> 'cancelled'` убирает отменённые подписки: они не оплачены и не должны входить ни в сумму, ни в долю.
- Цена берётся из каталога тарифов (`subscriptions.price`).

**Контрольный результат** (`Control Viewer One`):

| Тариф | Цена | Всего | Доля |
|---|---|---|---|
| basic | 299.99 | 1899.97 | 15.8 % |
| standard | 599.99 | 1899.97 | 31.6 % |
| premium | 999.99 | 1899.97 | 52.6 % |

Отменённая вторая подписка `premium` не учтена. Сумма долей даёт 100 %. У `Control Viewer Two` одна подписка и доля 100 %.

## 5. Часть 2. Обычные представления

**Представление (`VIEW`)** хранит не данные, а сам запрос. Каждый раз, когда к нему обращаются, запрос выполняется заново, поэтому результат всегда актуален.

### 2.1. Операционное представление `v_subscription_details`

Единый список подписок: пользователь, его почта, тариф, цена, период и статус. Объединяет три таблицы (`active_subscriptions`, `users`, `subscriptions`), поэтому оператору не нужно каждый раз писать `JOIN`.

**Демонстрация актуальности** (внутри транзакции с откатом, чтобы данные не менялись). Для пользователя `alex.kuznetsov@mail.com`:
1. до изменения: 4 подписки, последняя `active`;
2. после изменения исходных таблиц (подписка отменена, добавлена новая на `premium`): то же представление показывает последнюю как `cancelled` и новую строку `premium`; ничего пересоздавать не пришлось;
3. после `ROLLBACK`: снова 4 подписки, последняя `active`.

### 2.2. Аналитическое представление `v_movie_popularity`

Построено на запросе 1.1 (рейтинг популярности фильмов в жанре). Дальше его можно использовать как обычную таблицу.

**Использование в другом запросе:** для каждого жанра выбираются фильмы на первых двух местах (с учётом совпадений) и считается, насколько их число просмотров отличается от среднего по жанру:

- фильтр `rank_in_genre <= 2 AND views_count > 0` использует готовый столбец из представления;
- среднее по жанру считается подзапросом по тому же представлению;
- разница (`diff_from_genre_avg`) это вычисляемый столбец.

Полезно то, что сложный запрос с оконными функциями написан один раз, а остальные отчёты строятся поверх него короткими запросами.

### 2.3. Изменяемое представление `v_active_subscriptions` (`WITH CHECK OPTION`)

Простое представление над одной таблицей (`active_subscriptions`) с условием `status = 'active'`. Через него можно редактировать только действующие подписки, например продлевать, и нельзя вывести подписку из состояния `active`.

| Операция через представление | Результат |
|---|---|
| `UPDATE ... SET end_date = end_date + 30` (продление) | **успешно**, строка изменена |
| `INSERT` новой подписки со статусом `active` | **успешно** |
| `UPDATE ... SET status = 'cancelled'` | **ошибка**: `new row violates check option for view "v_active_subscriptions"` |
| `INSERT` подписки со статусом `expired` | **ошибка**, та же причина |

Успешные операции выполняются внутри транзакции с откатом, чтобы данные не менялись. Две ошибки это нужный результат демонстрации.

Без `WITH CHECK OPTION` оба «ошибочных» изменения прошли бы: подписка просто исчезла бы из представления (для `UPDATE`) или была бы добавлена в таблицу, но не видна через представление (для `INSERT`).

## 6. Часть 3. Материализованное представление

### Что создано

`mv_monthly_genre_stats`: статистика по месяцам и жанрам. Для каждой пары «месяц + жанр»: число просмотров, число уникальных зрителей, средний прогресс просмотра, число досмотренных до конца. Чтение по месяцам выглядит так: «за март в жанре Comedy 3 просмотра, 3 зрителя».

Дополнительно создан уникальный индекс по `(period, genre_id)`. Он ускоряет поиск и нужен для обновления без блокировки читателей (`CONCURRENTLY`, см. часть 4).

### Чем отличается от обычного представления

Материализованное представление **хранит результат** запроса как таблицу. Читать его быстро, но данные остаются такими, какими были на момент последнего `REFRESH`.

### Почему именно этот запрос стоит хранить готовым

| Причина | Пояснение |
|---|---|
| тяжёлый запрос | группировка по всей истории просмотров с `COUNT(DISTINCT ...)`; таблица `viewing_history` самая быстрорастущая в системе (каждый просмотр новая строка) |
| читают часто, меняется редко | статистику по месяцам смотрят дашборды и аналитики постоянно, а закрытые месяцы не меняются вообще |
| результат маленький | десятки строк на месяц против миллионов строк истории |
| точность «до секунды» не нужна | для планирования закупки контента и маркетинга достаточно данных на вчерашний день |

**Что не стоит материализовать:** `v_subscription_details` (операционное представление), потому что оператор должен видеть актуальный статус подписки сразу. Для него достаточно обычного представления.

### Демонстрация отставания

В `05_materialized_view.sql` внутри транзакции с откатом:

| Шаг | `viewing_history` | `mv_monthly_genre_stats` |
|---|---|---|
| добавили новый просмотр | на 1 больше | **без изменений** (отстаёт) |
| `REFRESH MATERIALIZED VIEW` | на 1 больше | на 1 больше (догнало) |
| `ROLLBACK` | исходное | исходное |

## 7. Часть 4. Управление актуальностью данных

### Допустимая задержка

**Допустимая задержка актуализации: до 24 часов.**

Обоснование для предметной области:
- Просмотры регистрируются **непрерывно** (в течение суток тысячи новых строк), но статистика по жанрам и месяцам нужна для решений, которые принимаются в масштабе недель: какие жанры расширять в каталоге, какие лицензии продлевать, какие рекомендации усиливать.
- Решения не зависят от того, что произошло час назад. Отставание в сутки на выводы не влияет.
- Текущий месяц ещё не закончен, и его цифры всё равно предварительные.
- Закрытые месяцы после окончания не меняются (кроме исправления ошибок).

### Политика обновления

| Когда | Команда | Зачем |
|---|---|---|
| **Раз в сутки ночью** (например, в 03:00, когда нагрузка минимальна) | `REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_genre_stats;` | основное обновление, укладывается в допустимые 24 часа |
| **Первого числа месяца** (ночное обновление после полуночи) | та же команда | в статистику попадает полностью закрытый предыдущий месяц, его цифры становятся окончательными |
| **Вручную, по необходимости** | `REFRESH MATERIALIZED VIEW mv_monthly_genre_stats;` | перед важной отчётностью (встреча с руководством) и после массовой загрузки или исправления истории просмотров |

Почему так, а не иначе:
- **Не раз в час.** Каждое обновление пересчитывает всю историю. Нагрузка выросла бы в 24 раза, а пользы для решений нет.
- **Не раз в месяц.** Цифры текущего месяца были бы старыми на несколько недель, мониторинг стал бы бесполезным.
- **`CONCURRENTLY`** обновляет представление, не блокируя читателей: дашборды продолжают работать во время пересчёта. Для этого и нужен уникальный индекс. Без `CONCURRENTLY` обычный `REFRESH` на время пересчёта блокирует чтение.
- **Автоматизация не требуется** по заданию. В реальной системе ночное обновление запускали бы планировщиком (cron, `pg_cron`).

Как заметить отставание: сравнить число строк в источнике и сумму в представлении (запрос из демонстрации):

```sql
SELECT (SELECT COUNT(*) FROM viewing_history) AS source_views,
       (SELECT SUM(views_count) FROM mv_monthly_genre_stats) AS mv_views;
```

Разница показывает, сколько просмотров ещё не учтено.

Возможное развитие: если история станет очень большой, закрытые месяцы можно хранить отдельно и пересчитывать только текущий. В рамках этой работы это не требуется.

## 8. Мини-теория простыми словами

| Понятие | Суть |
|---|---|
| оконная функция | считает по «окну» связанных строк, **не схлопывая** их (в отличие от `GROUP BY`) |
| `PARTITION BY` | разбивает строки на независимые окна (по жанру, по пользователю) |
| `ORDER BY` внутри `OVER` | задаёт порядок строк внутри окна |
| `RANK()` | место с пропусками после совпадений (1, 1, 3) |
| `DENSE_RANK()` | место без пропусков (1, 1, 2) |
| `ROW_NUMBER()` | уникальный номер, равных мест нет (1, 2, 3), для совпадений порядок зависит от сортировки |
| `LAG(x)` | значение `x` из предыдущей строки окна (`NULL` для первой) |
| `LEAD(x)` | значение `x` из следующей строки окна |
| `SUM(x) OVER (PARTITION BY ...)` | сумма по группе, но строки остаются отдельными |
| `VIEW` | сохранённый запрос, данные не хранит, всегда актуален |
| `WITH CHECK OPTION` | запрещает изменения через представление, после которых строка перестала бы подходить под его условие |
| `MATERIALIZED VIEW` | сохранённый **результат** запроса, быстро читается, но устаревает до `REFRESH` |
| `REFRESH ... CONCURRENTLY` | обновление без блокировки читателей, требует уникальный индекс |

## 9. Вопросы, которые могут задать на защите

- **Чем `GROUP BY` отличается от оконной функции?** `GROUP BY` схлопывает строки в одну на группу, оконная функция считает по группе, но все строки остаются.
- **Почему в 1.1 использован `RANK`, а не `ROW_NUMBER`?** Фильмы с равным числом просмотров должны получить одинаковое место, а `ROW_NUMBER` всегда даёт разные номера.
- **В чём разница между `RANK` и `DENSE_RANK`?** После совпадения `RANK` пропускает номера (1, 1, 3), `DENSE_RANK` нет (1, 1, 2).
- **Как в 1.1 фильмы без просмотров не пропадают из результата?** `LEFT JOIN` сохраняет все фильмы, а `COUNT` по столбцу правой таблицы даёт 0.
- **Зачем в окне 1.2 вторым ключом сортировки `history_id`?** Чтобы порядок был однозначным, если у двух просмотров одинаковое время.
- **Что вернёт `LAG` для первого просмотра пользователя?** `NULL`: предыдущего нет, но строка остаётся в результате.
- **Почему в 1.3 отменённые подписки исключены?** Они не оплачены и не должны входить в сумму трат и долю.
- **Чем представление отличается от материализованного?** Обычное хранит запрос и всегда актуально, материализованное хранит результат и обновляется командой `REFRESH`.
- **Зачем нужен `WITH CHECK OPTION`?** Чтобы через представление нельзя было изменить строку так, что она перестанет ему соответствовать (например, отменить подписку через представление активных подписок).
- **Почему материализуется именно статистика по месяцам?** Тяжёлая группировка по самой большой таблице, результат маленький, читают часто, закрытые месяцы не меняются, точность до секунды не нужна.
- **Какая допустимая задержка у вашего материализованного представления и почему?** До 24 часов: решения принимаются в масштабе недель, а не часов.
- **Зачем уникальный индекс на материализованном представлении?** Он нужен для `REFRESH ... CONCURRENTLY`, который не блокирует читателей во время обновления.
